Critical-hit tables: what a crit did, and the message that announces it.

2,394 entries across 21 damage types, each with the regex that recognises its message. Knowing them means a crit is understood the moment it lands, rather than being re-derived from what it did.

§Shape

  • crit/types.rs – the vocabulary: the enums an entry is built from.
  • crit/entry.rs – CritEntry, one row of one table.
  • crit/load.rs – parsing data/crit_tables.tsv, the shipped data.
  • crit/match_index.rs – the first-word bucket index, and the one pattern Rust’s regex cannot compile.

The data is a checked-in TSV rather than generated Rust: it is static data, and generated Rust would be 21 times the size once formatted. crit/load.rs’s module docs carry that measurement.

§Regenerating the data

ruby crates/hydra-model/tools/extract_crit_tables.rb \
     <critranks source directory> \
     crates/hydra-model/data/crit_tables.tsv

cargo test never runs the extractor and never needs Ruby: the TSV is the checked-in ground truth, and tests/crit_parity.rs holds it to the digest recorded when it was extracted.

§No process global

CritTables is an ordinary value. Build it once and share it as Arc<CritTables>; there is no static and no OnceLock. Multi-session depends on the model holding no process-wide state, and a 2,394-pattern table is precisely the thing that “just this once” gets made global.
