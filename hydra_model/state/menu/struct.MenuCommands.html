pub fn command_for( &self, coord: &str, noun: &str, exist: &str, secondary: Option<&str>, ) -> Option<String>

The command for one coordinate, with placeholders filled.

Three placeholders:

  • @ becomes the noun, e.g. "attack @" -> "attack kobold".
  • # becomes # followed by the exist id, e.g. "attack #" -> "attack #12345". The hash stays: it is the game’s syntax for addressing an object by id, not a placeholder marker.
  • % is a secondary argument the caller supplies – a second item for "transfer # %", a demeanour for "demeanor % @". Left in place when secondary is None, so a caller can see it is still needed rather than sending a malformed command.

MEASURED across an older 592-entry copy: 336 use #, 120 use @, 20 use %.

pub fn resolve_item( &self, item: &MenuItem, (exist, noun): (&str, &str), secondary: Option<&str>, learned: Option<&LearnedCommands>, ) -> ResolvedItem

Resolve one wire item for the object clicked, exist and noun, consulting what the server has taught us first.

An unknown coordinate resolves to an item with no label and no command rather than to nothing: the game sent it, so the player has it, and a silently shortened menu is worse than a visibly unnamed entry.

§Whose noun is which

@ is the object clicked, # its id: “@ substitutes the object’s noun and # substitutes its exist id”, as the protocol documents it. An <mi noun=> is the item’s own word, and it fills %: a captured menu sends ask @ about % (2524,1906) three times, as noun="amplify", "codex" and "shatter" (crates/hydra-protocol/tests/menu_responses.rs), so the command is ask #<id> about amplify. A secondary the caller supplies wins over the item’s word.

Filling @ with the <mi> noun instead would build ask amplify about % and, for the 169 entries whose command has @ and no # (tell @, sheathe @), send the verb alone on every item without a noun – nearly all of them.

pub fn resolve( &self, menu: &Menu, clicked: (&str, &str), secondary: Option<&str>, learned: Option<&LearnedCommands>, ) -> Vec<ResolvedItem>

Resolve a whole <menu>, in wire order.

exist is the caller’s, not the menu’s. Menu::id is a request sequence number – the corpus shows id="1", "2", "3" – so it answers which request is this and never which object. The object is whatever the player right-clicked, which only the caller knows.

pub fn resolve_grouped( &self, menu: &Menu, clicked: (&str, &str), secondary: Option<&str>, learned: Option<&LearnedCommands>, ) -> Vec<(Option<String>, Vec<ResolvedItem>)>

Resolve a menu and group it into categories, in the order the wire asked for.

<menu cat_list="1 2 3 4 …"> is the game stating how to present the categories, so it leads. Categories the items use but cat_list did not name follow, in first-seen order, rather than being dropped – the dictionary and the wire disagree about categories often enough that its list cannot be treated as exhaustive.

Items with no category at all – an unknown coordinate the wire did not place either – come last under None.
