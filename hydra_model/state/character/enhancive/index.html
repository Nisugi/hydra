Enhancive totals: six sections, a clique, and a static key space.

INVENTORY ENHANCIVE TOTALS reports every bonus an equipped enhancive item is currently granting.

§The key space must be known statically

The game’s output only shows non-zero values. A store with no deletion keeps a stale bonus from a removed item forever, so every key must be zeroed before every parse – 191 keys (MEASURED: 10 stats + 46 skills x 2 + 5 resources + 80 cman martial + 1 spells + 3 statistics).

Typed fields give that for free – Default is the zeroing – and every group here maps onto a type this crate already has: StatKind, SkillKind, and the open PSM mnemonic set.

§The section headers are a CLIQUE, not a chain

Any section may follow the report’s opener or any other section, because a character with no enhancive skills simply has no Skills: section. MEASURED in the capture, the order is:

Stats:  Skills:  Resources:  Self Knowledge Spells:  Martial Knowledge Skills:  Statistics:

Spells come before Martial. A reader that assumed some other fixed order would mis-section every martial row.

§Two forms, and the longer one is not the shorter one with extras

MEASURED in the captured DETAILS output:

Stats:
  Wisdom (WIS): 15/40
    +10: a veniom-bound witchwood badge      <- an item's share of the total
    +5: a gilded locus

The item-attribution lines are an extra layer, and the martial skills’ line shape inverts between the two forms:

  Coup de Grace: +2 ranks                                    <- short
  +2 Ranks Coup de Grace: a pallid jade green dragonfly tattoo <- details

A reader requiring name: +N ranks would drop every martial row of the details form. This module reads both.

§The headers arrive BOLDED

<pushBold/>Stats: on the wire. Bold is not required here – the literal is unambiguous – but it is recorded because it is a third independent signal, and because a section header is exactly the thing a future format change would re-style.
