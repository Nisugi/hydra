Expand description

What the wire has told one character so far.

None throughout is “not told”, never a default the game did not send.

pub const fn game_time(&self) -> Option<u32>

The last prompt’s own server time, unextrapolated.

What a RECORD of the past wants: it is a fact of the stream, so a replay reads the same value. Self::game_time_now moves with the wall clock between prompts, which is what “is my roundtime over” wants and what a recorder must not use.

Source

pub fn game_time_now(&self) -> Option<u32>

The server’s clock now, extrapolated.

The last prompt’s timestamp plus how long ago it arrived on the local monotonic clock. The single most important idea in this file.

§Why extrapolate rather than read a clock

Timers must keep flowing between prompts. A prompt is sent when something happens; nothing is sent when a roundtime merely ends. MEASURED: a session with a behavior firing once a second produced 58 prompts, and an idle one would produce none – so anything that waits for a prompt to learn a roundtime ended waits forever in a quiet room.

Both sides stay in server time, so clock skew cancels instead of needing correction. This is what made an elaborate skew-calibration design unnecessary: there is no comparison between two clocks anywhere in it, only an interval measured on one.

Returns None until the first prompt arrives – unknown, not a fabricated zero.

Source

pub fn game_time_after(&self, elapsed: u32) -> Option<u32>

Self::game_time_now with the elapsed interval supplied rather than read from the local clock.

§Why this exists

game_time_now reads Instant::elapsed, and a test cannot control it. hydra-model deliberately has no tokio dependency, so start_paused – the usual lever for this in async code – is not available here: pulling an async runtime into the model crate to make one assertion deterministic buys determinism with the layering the workspace exists to enforce.

So the interval becomes a parameter. Production still measures it; a test states it, and states 0 when it means “at the instant the prompt arrived”.

This is not a test-only method. A caller that already knows how much time has passed – a replay, a recorded session, anything driving the model from a timeline rather than from the wall clock – wants exactly this, and running many sessions in one process makes that likelier, not less.

§Why a test needs it

A test that pins a prompt second and asserts the clock equals it, through the wall clock, holds only while the suite runs inside one second of wall time: a slow machine crosses a boundary and reads one second later. Not a flake – a real dependency on how long the process has been running.

Source

pub fn in_roundtime(&self) -> Option<bool>

Whether the character is in roundtime.

Compares the extrapolated server clock against Self::roundtime_ends, both in server epoch seconds.

§This test is EXACT, not approximate

MEASURED: across three roundtimes the first plain > prompt landed precisely on <roundTime value=>, so value is the end instant rather than “somewhere inside that second”.

§None means unknown, and unknown is not false

Returns None when the clock is unobserved – no prompt has arrived, so there is nothing to compare against. A caller that treats that as “not in roundtime” is inventing a belief, and the type makes them write the decision down.

§A roundtime that was never reported is OVER, not unknown

When roundtime_ends is None, no roundtime has ever been reported, and that is the normal state at login: a character who has done nothing has no roundtime, and the first <roundTime> may not arrive for minutes. Reading it as unknown would have every send_now refuse for the whole of that window – the feature disabled exactly when a fresh character is most likely to want a sigil. An unreported roundtime is in the past, not unheard-of.

The asymmetry is the point: the clock is a fact about the connection that must be observed before anything can be compared, and the roundtime is a fact about the character that has a meaningful default. Concluding “a roundtime nobody has ever mentioned is not running” invents nothing.

pub fn knows_spell(&self, number: u16) -> Option<bool>

Whether a spell is known.

The rule is (num % 100) <= ranks — the spell’s position within its circle against ranks in that circle — with three refinements:

  1. Ranks are capped by level: the lesser of circle ranks and level. A character with 30 circle ranks at level 10 knows the 10th spell, not the 30th.
  2. Circles 97, 98 and 99 use SOCIETY rank, not circle ranks — and only while a member of that society. Those are Sunfist, Voln and the Council, so this matters to two of the five ways home.
  3. Circle 17 is profession-gated and circle 96 is always false. Arcane is known only to a Wizard, Cleric, Empath, Sorcerer or Savant, and only spell 1700; circle 96, Combat Maneuvers, is not spells at all.

None when an input has never been read. Not answered: a spell granted outside the rank rules (self-knowledge), which needs a feature Hydra does not have.

pub const fn answer_idle_warning(&mut self)

The character acted, so the warning is answered.

Called by the session actor on every outbound write, because only an outbound command answers an idle warning and this model is inbound-only.

The obvious alternative – clear it on the next <prompt> – is wrong, and measurably so: in a recorded session the character idled on for minutes after the warning while prompts arrived every few seconds, driven by dialogData id='Buffs' refreshes and a bystander’s emote. A prompt means something happened, not that the player did something.

Idempotent, and cheap enough to call unconditionally: it is one enum store on a path that is already doing a socket write.

pub fn resolve_noun(&self, noun: &str) -> Vec<Found<'_>>

Every thing currently known by this noun.

Searched in a defined order – creatures, room objects, players, then containers by id – so the result is deterministic for a replay and so .first() means something stable to a caller who uses it.

Creatures come first deliberately: a noun that matches both a creature and a floor item is overwhelmingly meant as the creature, because that is what a player is usually acting on.

Returns every match rather than the best one. The game disambiguates with ordinals, so guessing here would send a command at the wrong target and report success. See the module docs.

pub fn find_by_id(&self, id: &str) -> Option<Found<'_>>

The thing with this exist id, wherever it is.

The unambiguous lookup: ids are unique where nouns are not, so this returns at most one. What a consumer uses once it has chosen among Self::resolve_noun’s answers and wants to check the thing is still there before acting.

pub fn find_items(&self, name: &str) -> Vec<Match>

Every item this name could mean, best first.

Sends nothing – it reads the hands, the ready list and the inventory this state already holds, so the answer is only as good as what the game has said. A caller that needs certainty refreshes inventory first, which is a behavior’s job.

Ordered by Specificity then Location: the order the game itself resolves a bare noun in. Duplicate ids collapse; items with the same name collapse too, because they are interchangeable – and a caller picking between two identical names has no basis to choose.

pub fn carries(&self, id: &str) -> bool

Whether the object with exist id id (a leading # allowed) is known to be the character’s own: in a hand, worn, named by a stow or ready slot, in the inventory tree, or listed inside a container window whose object is one of those.

Known, not merely possible. false for anything the model has not seen as carried – an object in the room, a player, a bin, or an item of the character’s the game has not listed yet – so a caller that must never put something where it is lost refuses on false.
