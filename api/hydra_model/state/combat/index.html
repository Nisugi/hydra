Combat: the classifiers over one chunk line.

The combat definition grammar – what an attack, a roll, a damage line, a flare, a status or an outcome looks like – as stateless classifiers, the shape every other classifier in this crate takes.

§The patterns are data, generated by a committed tool

tools/extract_combat_defs.rb writes three TSVs by the part of an exchange they describe:

FileFamiliesRows
combat_attacks.tsvinitiations, their prefixes, the coup kill line376
combat_results.tsvdamage, the eight roll grammars, outcomes222
combat_effects.tsvflares, statuses, spell losses, brackets, UCS356

954 rows, first-match-wins within each family. The order column is that position and the loader keeps it, because it is load-bearing: priority definitions come before generic swings, and second person before third.

A fourth file, combat_flare_mirror.tsv (277 rows, family flare_mirror), generated by tools/extract_flare_mirror.rb, holds further flare wordings and is read by flare only after the main flares.

§Patterns run against PLAIN text

A ChunkLine is plain text with every link kept beside it as a typed Run, so no pattern needs optional groups to tolerate a <pushBold/> or an <a ...> falling inside the text. VERIFIED at extraction: zero residual tags in any non-flagged row.

Eight patterns read the exist id out of the tag itself – <a exist="(?<id>\d+)" – and cannot be plain text. They are flagged markup=1 in the data and written by hand in defs::HAND_PORTED, each as a text capture plus a link-position lookup. The loader substitutes them by (family, order), so their position in the first-match order is kept, and a test asserts every flagged row has a replacement.

§Links from run positions, not re-scanning

target answers “which link, which noun, was it bold” from run positions: a capture’s byte span overlaps some runs, and the runs carry the links. Nothing re-scans the matched text for markup, so the possessive inside a link – a capture ending at the apostrophe of <a>skald's</a> – is not a special case at all, because a span that ends inside a run still overlaps it.

§The gate, measured

A performance conclusion is only as good as its measurement here. Each family carries a RegexSet (defs), and the crit index one over its unanchored residual (crit/match_index.rs). crit/match_index.rs records RegexSet as the slowest option at 2,394 patterns; at 9 to 362 per family, with a raised DFA budget, it is the fastest thing measured.

MEASURED, release, warm caches, the 85 replay blobs:

                                 linear      gated
every family once per line      105 us      3.6 us    (tests/combat_gate.rs prints its own)
CritTables::parse, per call    17-20 us     1.6 us
the state machine, per line     142 us       10 us
parser + chunk + FSM            ~145 us      13 us    (tests/combat_replay_events.rs)

A cold pass is not a measurement: ~100ms of one is compiling the tables, and a regex also builds its DFA lazily, so every timing here runs an untimed pass first.

Classify-once-per-line was considered and not done. The machine asks DamageLine up to four times a line and FlareLine twice; with the gate each ask is ~0.2-0.4us, so the whole redundancy is under 3us of the 10. Threading a cache through eight branch modules to win that is not KISS.

tests/combat_gate.rs proves the gate agrees with a linear scan on every fixture line in every family and role, and that no family fell back.

§Not here

  • Incident messages live in state/incident.rs; the state machine never reads them.
  • User-supplied patterns. There is no pattern scripting.

§The consumer above the classifiers

parse is the state machine these classifiers feed, and tracker is what it keeps between chunks. GameState::close_chunk hands every prompt-bounded chunk to CombatTracker::consume_chunk; the event types are what comes out.
