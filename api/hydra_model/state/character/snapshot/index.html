What persists between sessions, and how it goes stale.

The model half. The I/O half is the session’s character store; this file is the shape on disk and nothing else, so hydra-model stays free of the filesystem.

§The store is the primary record, not a cache

It is persisted, in parts. A command run by hand populates it, ordinary play keeps it updated (training sends its own report), and there is a way to reset and refresh it.

That is the design constraint. Most of what is here can only be taught by a command a person runs by hand – info, skills, the five PSM lists, inventory enhancive totals. A model rebuilt each session would show a character with no stats until someone typed info, so the file on disk is the record and the wire merely updates it.

It is also why Group exists. “Reset and refresh” needs to know which group is stale, and a single whole-file timestamp cannot answer that: a character who ran skills this morning and info last month has one fresh group and one ancient one.

§Why serde and not a database

The access pattern does not want a database. Every read is “give me this character’s stats”; there are no queries, no joins, and one writer. Typed fields serialize as they are.

§Staleness is a version AND a timestamp, per group

A parser change invalidates stored values, so a snapshot written by an older SCHEMA_VERSION is not trusted: the classifier that produced it may have read a column differently.

A per-group timestamp plus a schema version is both halves: the version answers “can this file be believed at all”, and the per-group stamp answers “which command should be re-run”.
