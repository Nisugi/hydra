Expand description

One thing the game said.

Frame::UnknownTag and Frame::MalformedTag exist, and neither is optional, because Simutronics changes the protocol without notice: an unmodelled tag must reach the user as text and a log, never panicking and never silently dropped.

Variants (Non-exhaustive)§

This enum is marked as non-exhaustive
Non-exhaustive enums could have additional variants added in future. Therefore, when matching against variants of non-exhaustive enums, an extra wildcard arm must be added to account for any future variants.

PlayerId

<playerID id=>: the game’s number for this character, sent once in every login burst.

Typed for Frame::EndSetup’s reason: a consumer keys on it (the model’s “is that link me?”, for the group’s leader), and matching a WindowHints bag by its id string is re-reading markup. id is the tag’s one attribute, a number, so nothing the bag carried is lost.

Fields

§id: String

id=, verbatim; empty when absent.

§

SettingsInfo

<settingsInfo client= major= crc= instance=>: which of the game’s instances this connection plays, by the game’s own code, and the client settings it expects. Sent once in every login burst (tests/fixtures/login_setup.xml).

Typed for Frame::PlayerId’s reason: a consumer keys on it. The model keeps instance, which is how Lich knows which game it is in, for a Lich handed the login late; and matching a WindowHints bag by its id string is re-reading markup. The other attributes ride in attrs, so nothing the bag carried is lost.

Fields

§instance: Option<String>

instance=, verbatim; None when absent.

§attrs: Attrs

Every attribute, in wire order.

§

EndSetup

<endSetup/>: the login setup is over. The session keys Ready on the first <prompt> after it. Typed rather than left in a WindowHints bag, which a consumer could only recognise by string; unit because the tag has no attributes, and every one seen in recorded sessions is bare.

§

AppInfo

<app char= game= title=> – who this connection is, and where.

game is the INSTANCE, and a multi-session client needs it. The wire sends <app char="Alderin" game="Prime" title="GemStone IV: Alderin [Prime]"/> (as in tests/fixtures/login_setup.xml), and Prime, Platinum, Shattered and Test are separate worlds: the same character name in two of them is two different characters.

title is kept rather than derived: it is what the game says to put in a window title bar, and reassembling it from the other two would be guessing at a format the server already sent.

Fields

§character: String

char=: the character’s name; empty when absent.

§game: String

The instance: Prime, Platinum, Shattered, Test.

§title: String

The window title the game suggests, verbatim.

§

RoomId

<nav rm=> – the room changed. None for a bare <nav/>: a real shape meaning “arrived, and this room has no UID” (DragonRealms sends it). An empty string here could not be told from a UID.

Fields

§id: Option<String>

rm=, entity-decoded; None for a bare <nav/>.

StreamWindow

<streamWindow id= title= subtitle= ...>.

id, title and subtitle are lifted because windows render them. Everything else rides in attrs rather than being dropped: a census of a 1,547-file corpus sample found 1,176,686 <streamWindow> carrying 15 distinct attribute names, of which only three were kept. location (1,169,402) and target (1,163,813) are on ~99% of them, and ifClosed (602,513), resident (605,219) and styleIfClosed (1,353) are all live.

Fields

§id: String

id=: the stream this window shows; empty when absent.

§title: Option<String>

title=; None when absent.

§subtitle: Option<String>

subtitle=; None when absent.

§attrs: Attrs

Every attribute the tag carried, including the three above.

§

InjuryImage

<image id= name=>, and which dialog enclosed it.

The name says injuries because that is the one use worth modelling, but the tag is not exclusive to them: MEASURED over 24 files, 1,313 of 2,155 <image> tags are nomap.jpg map tiles and ~50 are toolbar buttons. dialog is what separates them, exactly as it does for ProgressBar – the same tag shape meaning different things depending on the dialog that encloses it.

Fields

§id: String

id=. The body part, when dialog is injuries.

§name: String

name=. The severity (Injury1..Scar3), or the part’s own name when it is unhurt.

§dialog: Option<String>

The enclosing <dialogData id=>, if any.

§attrs: Attrs

Every attribute, in wire order. Not only layout: the toolbar <image>s in inventory_container.xml carry cmd=, echo= and tooltip= – a button’s whole behaviour – beyond id and name.

§active: bool

ObjectivesUpdate

<objectives action=> and the <objective> rows it carries.

One frame, like Frame::MenuResponse and for the same reason: as separate frames the rows would land in Frame::WindowHints – the placement-attrs bag, which is not what a quest is – apart from the action. An update that says delete-objective is meaningless apart from the rows it deletes.

Fields

§action: ObjectivesAction

What to do with entries.

§entries: Vec<Objective>

The rows, in wire order.

§

MenuResponse(Menu)

A context menu the game built for one object: <menu> and its <mi> items, as one frame.

As separate frames the items would carry an empty id, orphaned from the menu they answer, and no consumer could tell which request they belonged to. A menu opens and closes on one line, even one of 60 items, so the envelope is assembled here, as <component> is.

§

CmdListUpdate(CmdListUpdate)

<cmdlist>: dictionary rows the server is teaching us.

One frame carrying its <cli> children, for the same reason Frame::MenuResponse is: the rows are the payload, and as separate WindowHints bags nothing would join them.

§

CmdTimestamp

<cmdtimestamp data=>: the dictionary version the server just sent.

Separate from Frame::CmdListUpdate because the wire sends it as a separate tag, and because it is meaningful alone: a timestamp with no rows says the client is already current.

Fields

§version: String

data=, as sent; empty when absent.

ClientCommand

The player’s own typed command, echoed back in the log.

It arrives as <!-- CLIENT --><c>;go2 3609<!-- ENDCLIENT -->, and it is how a replay knows what the player did, which for a client that replays its own logs as test fixtures is the difference between a reproducible session and a one-sided transcript.

Fields

§command: String

The text after <c> in the region, e.g. ;go2 3609: entity-decoded, control characters stripped.

§

ClientSettings

The login <settings> blob arrived and was consumed whole.

A client-configuration document – window layout, palettes, highlight strings, macros – not game protocol. It carries dozens of element names of its own (h, dc, cmdline, ignores, panels, toggles, …), all on one line.

The frame records that the blob arrived, because a login is worth seeing in a replay; its contents are not modelled here.

§

UnknownTag

A tag this parser does not model, carried whole.

raw is the original bytes, so the tag reaches the user as text and a diagnosing reader sees exactly what the game sent. It is the one place raw markup crosses the vocabulary boundary.

It is a type of its own, not Text, so a consumer can tell “the game said something new” from “the game said hello”.

Fields

§name: String

The tag name, as spelled on the wire.

§raw: String

The tag as received; a close tag is rebuilt as </name>.

§

Structural

A tag that arrived and whose effect is not carried by any neighbouring frame’s fields.

Nothing that comes in is dropped: a known close form or self-closing form with nothing to model emits this, so every consumer can see it.

Distinct from Frame::UnknownTag on purpose: an UnknownTag means the protocol changed and someone should look, a Structural means the protocol did exactly what it always does and there is nothing to model. Collapsing them would cry wolf on every </a>.

raw is the original bytes, so nothing is unrecoverable. Use Frame::is_structural to filter these out; most consumers want to.

Fields

§name: String

The tag name, e.g. a for a </a>.

§raw: String

The tag as received; a close tag is rebuilt as </name>.

§

MalformedTag

A tag that cannot be read: one that never closed before the line ended, or a timer whose value is not a number.

Treating the unclosed fragment as text would silently desync the stream. Typed here so the case is visible, testable, and cannot be mistaken for prose. A timer read as zero instead would end a roundtime the game never ended.

Fields

§raw: String

The tag as received: the unterminated text through the end of the line, or the whole timer tag.
