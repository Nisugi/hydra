1//! The HTTPS web-login fallback: a second way in when eaccess is down.
2//!
3//! # Why this exists
4//!
5//! **It is the outage path.** eaccess has gone down -- `eaccess.play.net:7910`
6//! silently dropping the SYN, no RST -- while website sign-in and
7//! Play-in-Browser stayed up throughout.
8//!
9//! So this is not a nicety. When it matters, it is the only way in.
10//!
11//! # An entirely different mechanism
12//!
13//! [`eaccess`](crate::eaccess) is tab-delimited records over a raw TLS socket
14//! with a client-side XOR-hashed password. This is ordinary HTTPS: ASP form
15//! POSTs, a session cookie, and a redirect chain whose **target path** is the
16//! success/failure signal. It ends at the same place -- a game host, a port and
17//! a one-shot key.
18//!
19//! Three consequences worth stating, because each one inverts something the
20//! eaccess module establishes:
21//!
22//! | | eaccess | here |
23//! |---|---|---|
24//! | the password | XOR-hashed against a server nonce | **sent in the clear** as a form field |
25//! | TLS | 1.2, static-RSA, self-signed, three documented weakenings | 1.3, valid chain, ordinary verification |
26//! | the character list | the `C` command, tab-delimited | **scraped out of HTML** |
27//!
28//! The password point is not a flaw to fix: play.net's form takes a cleartext
29//! field and security rests entirely on TLS. It is recorded so nobody ports
30//! eaccess's hashing here expecting it to apply, and so the cert verification
31//! is never relaxed the way [`live`](crate::live) deliberately relaxes it for
32//! eaccess -- `www.play.net` negotiates TLS 1.3 with a valid chain, so none of
33//! those weakenings have a reason to travel.
34//!
35//! # Behaviours that cannot be re-derived offline
36//!
37//! Six behaviours in this flow are invisible in a browser capture and only
38//! surface from a standalone client run against several accounts. Each is
39//! handled at the place it bites:
40//!
41//! 1. a browser-like **`User-Agent` is mandatory on every request**, including
42//!    the first GET -- play.net's WAF returns a bare 500 otherwise ([`http`]).
43//! 2. the login POST needs a **session cookie from a prior GET** of the sign-in
44//!    page; posting cold also returns a bare 500 ([`http`]).
45//! 3. an account with no security question is redirected **to a different page
46//!    on success** ([`scrape`]).
47//! 4. a character can exist on one instance and not appear on its family's
48//!    generic page at all ([`instance`]).
49//! 5. an account without a subscription gets a **second** redirect that a
50//!    non-following client never sees ([`scrape`]).
51//! 6. that redirect's path is **instance-specific**, so it is matched by shape
52//!    ([`scrape`]).
53//!
54//! No test logs into a live service, so none of these can be re-observed by
55//! the test suite. Every one is therefore a **test against a recorded
56//! fixture**, and the fixtures are the record.
57//!
58//! # Layout
59//!
60//! [`instance`] is the table: which page to scrape and which host the answer
61//! must name. [`scrape`] is the **pure** half -- responses in, verdicts out --
62//! and carries every test. [`failure`] is what went wrong and whether anything
63//! else should be tried. [`http`] is the half that touches the network, and is
64//! the only part a live run can check.
65

67pub mod http;
