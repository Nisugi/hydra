1//! Game-specific data, kept under a game namespace.
2//!
3//! Hostnames, endpoint tables and anything else that names one game's
4//! servers live here, directly under `src/gemstone/`, so shared modules stay
5//! free of them. The modules here hold **data**: lookup tables of opaque
6//! endpoint strings, with no `if game == ...` branch anywhere in them.
7//!
8//! # The `DragonRealms` rows, under a `gemstone/` path
9//!
10//! [`endpoint`]'s fourth row maps `prime.dr.game.play.net:4901` to
11//! `dr.simutronics.net:11024`. That is a `DragonRealms` endpoint sitting under
12//! `gemstone/`, which is **imprecise and deliberate**:
13//!
14//! - It is one row of a four-row table. Splitting the table to place one row
15//!   correctly would mean two tables and two lookups for no behavioural
16//!   difference.
17//! - `DragonRealms` support is deferred **all-or-nothing**. A `dragonrealms/`
18//!   directory created now to hold a single unreachable row would be the
19//!   first piece of exactly the structure that deferral exists to avoid.
20//!
21//! When `DragonRealms` is genuinely taken on, the row moves with the rest of the
22//! DR work. Until then it is inert -- Hydra never launches a DR game code.
23//!
24//! [`shim`]'s host remap has a `DragonRealms` row (`hydra.play.net`) on the same
25//! terms: it is one branch of a two-branch rule that play.net's browser client
26//! uses, and it is inert while no DR game code is launched.
