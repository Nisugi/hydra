1//! Two ways in, and the rule for choosing between them.
2//!
3//! # Why there is a second way in at all
4//!
5//! `eaccess.play.net:7910` goes down while the website stays up: the SYN is
6//! silently dropped, no RST, while website auth and Play-in-Browser keep
7//! working throughout.
8//!
9//! So the fallback is not redundancy for its own sake. It is the path that
10//! works on the days the main one does not.
11//!
12//! # The rule, and why it is the whole design
13//!
14//! **A credential rejection is never retried through the second system.** Web
15//! login would reject the same credentials too, so falling back would only
16//! resubmit them to a second system for no benefit. The real problem is
17//! surfaced instead.
18//!
19//! Two failures that both read as "login didn't work" need opposite responses,
20//! and both mistakes are expensive:
21//!
22//! | eaccess said | fall back? | cost of getting it wrong |
23//! |---|---|---|
24//! | the password is wrong | **no** | a second bad-password strike, and the real error is hidden behind a second failure |
25//! | I could not reach the server | **yes** | the session stays down through an outage the fallback would have survived |
26//!
27//! [`EaccessError::fatal`] already carries this distinction -- it exists
28//! because *one stage is both* -- so this module reads a decision that has
29//! already been made rather than making a new one. Note its default is
30//! `false`: an unclassified failure falls back, which is the direction that
31//! fails safe.
32//!
33//! # What the fallback cannot do
34//!
35//! Web login resolves **one character on one instance**. It has no equivalent
36//! of eaccess's `M` enumeration or the character generator, so those paths have
37//! no fallback.
38

43/// Which provider produced a launch.
44///
45/// Reported rather than hidden, because the two are not equivalent: a web-login
46/// launch came through an HTML scrape and a redirect chain rather than the
47/// `C`/`L` exchange, and a reader diagnosing an odd session needs to know
48/// which path produced it.
49#[derive(Clone, Copy, Debug, PartialEq, Eq)]
50pub enum Provider {
51    /// The `K A M F G P C L` exchange over TLS.
52    Eaccess,
53    /// The HTTPS web flow, after eaccess could not be reached.
54    WebLogin,
55}
56
57/// Which provider to try first, or to use alone.
58///
59/// # Why a forced web path exists at all
60///
61/// Because the fallback is otherwise **unreachable while eaccess is up**, and
62/// eaccess is up almost always -- which is the whole point of it. Without this,
63/// the web path could only ever be exercised during an outage, i.e. at the
64/// worst possible moment to discover a bug in it.
65#[derive(Clone, Copy, Debug, PartialEq, Eq)]
66pub enum Prefer {
67    /// The normal path: eaccess, with web login if it cannot be reached.
68    Eaccess,
69    /// **Web login only.** eaccess is not tried, so there is nothing to fall
70    /// back to and a failure here is final.
71    WebOnly,
72}
73
74/// Authenticate, choosing the provider -- and falling back to web login if
75/// eaccess cannot be **reached**.
76///
77/// # The order is not arbitrary
78///
79/// eaccess is tried first because it is the real protocol: it enumerates
80/// instances, it supports the character generator, and it returns what the
81/// launch needs without a scrape in between. Web login is narrower, so it is
82/// the fallback rather than the default even though it is more reliable on a
83/// bad day. [`Prefer::WebOnly`] exists so the web path can be exercised on a
84/// day when eaccess is healthy -- see [`Prefer`].
85///
86/// # Errors
87///
88/// The **eaccess** error, always -- even when the fallback also failed.
89/// `L` named the primary path, and its failure is the answer to "why could I
90/// not log in"; the fallback's failure is a footnote that would otherwise
91/// replace the real cause. The fallback's failure is passed to `progress`
92/// instead, so it is visible without being mistaken for the diagnosis.
93///
94/// Under [`Prefer::WebOnly`] the error is the **web-login** failure, since no
95/// eaccess attempt was made to have one.
96///
97/// A certificate that does not match `pin` is FATAL (see `pin.rs`), so it is
98/// returned as the diagnosis and web login is **not** tried: the operator must
99/// see that message, and a fallback that succeeded would bury it. `pin` is
100/// eaccess's alone -- the web path is verified TLS to www.play.net and does
101/// not read it.
102pub async fn authenticate_via(
103    creds: Credentials<'_>,
104    prefer: Prefer,
105    pin: &std::path::Path,
106    mut progress: impl FnMut(&str),
107) -> Result<(LaunchPayload, Provider), EaccessError> {
108    decide(
109        prefer,
110        &mut progress,
111        async |progress| super::authenticate(creds, pin, progress).await,
112        async |progress| try_web(creds, progress).await,
113    )
114    .await
115}

117/// The choice between the two providers, with the providers passed in.
118///
119/// # Why the stages are parameters
120///
121/// So that the RULE can be tested -- the thing this module exists for -- with
122/// no network. [`authenticate_via`] passes the real two; `fallback_tests.rs`
123/// passes stubs that fail on command and record whether they were called.
124///
125/// A test that asserts `.fatal` on an error it built itself never calls
126/// anything that reads it, so it stays green with the
127/// `if primary.fatal { return Err(primary) }` below deleted -- the line that
128/// stops a bad password being resubmitted to a second system.
129async fn decide<P: FnMut(&str)>(
130    prefer: Prefer,
131    progress: &mut P,
132    eaccess: impl AsyncFnOnce(&mut P) -> Result<LaunchPayload, EaccessError>,
133    web: impl AsyncFnOnce(&mut P) -> Result<Launch, WebLoginFailure>,
134) -> Result<(LaunchPayload, Provider), EaccessError> {
135    if prefer == Prefer::WebOnly {
136        progress("[login] web login FORCED; eaccess will not be tried");
137        let launch = web(progress).await.map_err(|f| web_only_error(&f))?;
138        return Ok((from_web(&launch), Provider::WebLogin));
139    }
140
141    let primary = match eaccess(progress).await {
142        Ok(launch) => return Ok((launch, Provider::Eaccess)),
143        Err(error) => error,
144    };
145
146    // **The rule.** A refusal is an answer, and the same credentials will be
147    // refused again. Falling back here would spend a second bad-password strike
148    // and bury the real cause under a second, less relevant failure.
149    if primary.fatal {
150        return Err(primary);
151    }
152
153    progress(&format!(
154        "[fallback] eaccess unreachable at stage {}; trying web login",
155        primary.stage
156    ));
157
158    match web(progress).await {
159        Ok(launch) => Ok((from_web(&launch), Provider::WebLogin)),
160        Err(secondary) => {
161            // Reported, not returned. See `authenticate_via`'s `# Errors`.
162            progress(&format!("[fallback] web login also failed: {secondary}"));
163            Err(carry_forward(&primary, &secondary))
164        }
165    }
166}

168/// A forced web login's failure, as the whole diagnosis.
169///
170/// No primary error to carry, so this is all there is -- and its fatality is
171/// decided differently from [`carry_forward`]'s, for one variant.
172///
173/// # `UnsupportedGameCode` is fatal HERE, and only here
174///
175/// In the fallback it is not: web login's table is narrower than eaccess's, so
176/// "web cannot route this code" says nothing about whether eaccess will, once
177/// it answers. Under [`Prefer::WebOnly`] there is no eaccess to answer. The
178/// table is compiled into this binary, so the verdict is identical on every
179/// attempt -- and a supervisor told "transient" re-runs it every 30 seconds
180/// forever, for a mistyped `GS4`.
181///
182/// `LoginRejected` is fatal for the reason it is everywhere: the credentials
183/// were refused. The rest stay transient for the reasons `carry_forward` gives.
184fn web_only_error(failure: &WebLoginFailure) -> EaccessError {
185    EaccessError {
186        stage: "web_login",
187        detail: failure.to_string(),
188        fatal: failure.is_credential_refusal()
189            || matches!(failure, WebLoginFailure::UnsupportedGameCode),
190    }
191}

193/// Run the web-login flow, narrating each stage.
194///
195/// Shared by both paths so the forced run exercises **exactly** the code the
196/// fallback would -- a forced path that differs from the real one tests the
197/// wrong thing.
198async fn try_web(
199    creds: Credentials<'_>,
200    progress: &mut impl FnMut(&str),
201) -> Result<Launch, WebLoginFailure> {
202    let request = WebLoginRequest {
203        account: creds.account,
204        password: creds.password,
205        character: creds.character,
206        game_code: creds.game_code,
207    };
208    let launch = authenticate_via_web(request, progress).await?;
209    progress("[web] authenticated via web login");
210    Ok(launch)
211}

213/// A web-login [`Launch`] as a [`LaunchPayload`].
214///
215/// # Nothing is synthesised
216///
217/// The web flow returns a host, a port and a key, and a [`LaunchPayload`] is
218/// exactly those three. It has no game code: the web flow does not return
219/// one, and filling it with the REQUESTED code (`GS3`) would put a second
220/// vocabulary beside eaccess's `L`, which names the server's family code
221/// (`GS`).
222fn from_web(launch: &Launch) -> LaunchPayload {
223    LaunchPayload {
224        gamehost: launch.host.clone(),
225        gameport: launch.port,
226        key: launch.key.clone(),
227    }
228}

230/// The eaccess error, noting that the fallback was tried and also failed.
231///
232/// The **stage and fatality are the primary's**, unchanged: the supervisor
233/// acts on those, and a web-login failure must not change what it does about an
234/// eaccess one. Only the human-readable detail gains a clause.
235///
236/// One exception, and it is the case that matters: if the fallback says the
237/// **credentials** are wrong, then both systems have now refused them and
238/// retrying is pointless. That is the one piece of information the fallback can
239/// contribute which the primary did not have.
240///
241/// # Why this matches one variant by name rather than asking a predicate
242///
243/// Because "fatal **for web login**" and "fatal **for this login attempt**" are
244/// different questions, and only one variant answers both. Four
245/// [`WebLoginFailure`] variants end a web-login attempt; three of them say
246/// nothing about whether eaccess would have succeeded:
247///
248/// | | fatal for web login | evidence against retrying at all |
249/// |---|---|---|
250/// | `LoginRejected` | yes | **yes** -- the credentials were refused |
251/// | `NoSubscription` | yes | no -- this instance, not these credentials |
252/// | `CharacterNotFound` | yes | no -- the scrape is the fragile part; eaccess enumerates properly |
253/// | `UnsupportedGameCode` | yes | no -- web login's table is narrower than eaccess's |
254///
255/// `CharacterNotFound` is the sharpest case. Web login finds characters by
256/// **scraping HTML**, which fails silently when the markup changes; eaccess
257/// asks the `C` command. So "web login could not find the character" is a
258/// statement about the scraper at least as often as about the account, and
259/// letting it stop the ladder would turn a play.net markup change into a
260/// permanently dead session.
261///
262/// Matching the one variant by name therefore is not a missed abstraction --
263/// it IS the distinction. `failure.rs` records why no four-variant predicate
264/// exists to be tempted by.
265fn carry_forward(primary: &EaccessError, secondary: &WebLoginFailure) -> EaccessError {
266    let credentials_refused = secondary.is_credential_refusal();
267    EaccessError {
268        stage: primary.stage,
269        detail: format!(
270            "{} (web-login fallback also failed: {secondary})",
271            primary.detail
272        ),
273        fatal: primary.fatal || credentials_refused,
274    }
275}
