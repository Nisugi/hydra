1//! `KNOWN_WIRE_TAGS`: every element name the wire is known to emit.
2//!
3//! The list is knowledge of the protocol that lives nowhere else: every tag
4//! seen in recorded traffic, every tag a dispatch arm handles, and tags the
5//! game's own client recognises though recorded traffic has not happened to
6//! carry them. It holds **130**, all distinct, ASCII-sorted;
7//! `the_table_holds_130_tags` asserts the number.
8//!
9//! # Entries worth a note
10//!
11//! - **`c`** -- the **echo of the player's own typed command**:
12//!   `<!-- CLIENT --><c>ask lu about bounty<!-- ENDCLIENT -->`, always inside
13//!   a `<!-- CLIENT -->` region. For a client that replays its own logs as
14//!   fixtures, the echo is how a replay knows what the player did.
15//! - **`map`**, **`mapInfo`** -- the automapper dialog, plain server output:
16//!   `<dialogData id='mapViewMain'><map id='mapViewMain' mapId='toadwort' ...>`
17//!   and `<mapInfo id='mapViewMain' pos='14017003'/>`.
18//! - **`streamBox`** -- a text box inside a dialog:
19//!   `<dialogData name="bugitemReport"><streamBox id="instructions" ...>`.
20//! - **`FEStart`** -- session start, sibling of `FEVersion`:
21//!   `<FEVersion="0" character="..." /><FEStart name="..."
22//!   time="1745968462" />`, where `name` is the game's own title. Rare: it
23//!   turned up only once a sample of recorded traffic reached 3,000 files.
24//! - **`style`** -- the room-name / room-desc preset switch, `<style
25//!   id="roomName" />` and `<style id=""/>` to close. Hundreds of thousands
26//!   of occurrences, handled as markup.
27//! - **`clearDialogData`** -- has a dispatch arm, and is listed on the
28//!   handler's authority though recorded traffic has not carried it.
29//! - **`closeContainers`**, **`room`**, **`task`** -- recognised by the
30//!   game's own client and absent from recorded traffic. A zero in a sample
31//!   means only that the sample did not contain it. `task` is an
32//!   `<objective>` child carrying quest progress.
33//! - **`group`** -- live in two distinct shapes: `<group id open>` client
34//!   settings, and `<group id type state cmd name>` inside `<objectives>`.
35//!
36//! **Why a corpus replay cannot check this table alone.** A replay counts
37//! `UnknownTag { name } if !is_known(name)`, but `is_known` is consulted only
38//! at the END of dispatch, after every explicit name arm. A tag that has its
39//! own arm never reaches the check, so its table entry is invisible to the
40//! replay -- and most entries have such an arm. Deleting one from the table
41//! would leave the replay green.
42//! `every_tag_with_a_handler_arm_is_in_the_table` is what makes the table and
43//! the dispatcher one fact instead of two.
44//!
45//! Two categories are deliberately **not** listed, because neither is game
46//! protocol and both are handled structurally in [`crate::parser`]:
47//!
48//! - The login `<settings>` blob's own element names (`h`, `dc`, `cmdline`,
49//!   `ignores`, `panels`, ...). It is a client-configuration document, and the
50//!   region is consumed whole.
51//! - Help text that merely looks like markup -- `<skill#>`, `<#ranks>`,
52//!   `<stat name>`. An XML name cannot contain `#` or a space; the text
53//!   scanner keeps these as prose (`text::is_prose`).
54//!
55//! XML comments (`<!-- ... -->`) are also real wire content and are handled in
56//! [`crate::parser`], not here: a comment is not an element and has no name.
57//!
58//! Nothing is removed lightly: a superset parser is more tolerant, never
59//! less, and removal is the risky act.
60//!
61//! # Why the table stays sorted, and why the test is not decoration
62//!
63//! [`is_known`] is a `binary_search`, so sort order is a correctness
64//! precondition, not tidiness. A mis-sorted insert makes *random other* tags
65//! report unknown, and they then spray into the user's text stream. The
66//! failure is silent and affects an arbitrary subset.
67//!
68//! The test can go RED: appending `"aaa"` to the end of the list fails the
69//! `windows(2)` scan immediately. The assertion is strict `<`, so it catches
70//! duplicates too -- a duplicate is harmless to `binary_search` but means
71//! someone added a tag that was already there and should know.
72//!
73//! The order is **bytewise**, so uppercase sorts before lowercase
74//! (`FEVersion` ... `PantheonStatus`, then `a`). A case-insensitive sort would
75//! disagree with `binary_search` and break exactly the tags it was meant to
76//! tidy.

234/// Is this element name one the wire is known to emit?
235///
236/// A `false` here does not mean the tag is invalid -- it means Simutronics
237/// changed the protocol, which must be surfaced rather than swallowed.
238#[must_use]
239pub fn is_known(name: &str) -> bool {
240    KNOWN_WIRE_TAGS.binary_search(&name).is_ok()
241}

243/// How many tags the table holds. Exposed so a test can assert the count
244/// without the table being public and mutable-looking.
245#[must_use]
246pub fn known_count() -> usize {
247    KNOWN_WIRE_TAGS.len()
