The player log’s writer.

Takes lines off super::LogSink and puts them on disk, one file per character per day.

§The shape

<log_dir>/player/<Character>/<Character>_2026-09-21.log
[06:47:12.481][main] You see a rock.

Three choices make it:

  • A file per character per day. A day is the unit a person searches in, and it makes rotation implicit rather than a size heuristic that cuts a hunt in half.
  • The date is in the filename, not the line. The wire log does the same: repeating the date on every line is waste. The stamp is hydra_net::line_time’s, so the two logs of one session line up by eye.
  • The stream tag is in brackets. A reader greps [death]; a future parser splits on the same bracket. One format serves both.

§Buffered, and written every few seconds

A flush hands the lines to the operating system, whose cache decides when the disk is touched. Rather than hand it every line as it comes, lines gather in a BUFFER-byte buffer, which goes to the file when it fills, every FLUSH_EVERY while anything waits, when a reader asks first (PlayerLog::flush, so the log window never reads short), and when the session ends. A crash loses at most the last FLUSH_EVERY. The timer lives in PlayerWriter::run, which owns the writer and so is the only thing that can flush it.

§What this does NOT do

It does not decide what gets logged. It writes what arrives. Deciding is the actor’s, and keeping that out of here is what lets a test drive the writer with three synthetic lines and no session at all.

It does not compress or prune. That is super::archive and super::retention.

Constants§

BUFFER
How many bytes gather before they go to the file on their own, between the timer’s flushes.
FLUSH_EVERY
Flush at least this often while anything is buffered: how much an abrupt exit can lose. Not how stale a read is: a reader asks for a flush first.
SUBDIR
The subdirectory under the log directory that player logs live in.
