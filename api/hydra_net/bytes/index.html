The byte source: where a session’s wire bytes come from.

§Why this is a trait

It has real implementors that are needed today, not one implementor and a guess at the future: LiveSource is the game connection, ReplaySource plays a recorded session back deterministically in a test with no network, and AnsweringSource stands in for the game in tests.

§Why it yields BYTES, not lines and not frames

Lines would duplicate work that already exists. Parser::push_bytes (in hydra-protocol) is the read boundary: it buffers until a newline, so a tag split across two TCP reads is rejoined before parsing. Its own doc says so, and the split-at-every-byte-offset test lives beside it. A line-yielding transport would reimplement that reassembly one layer down, in a place no test drives at every offset.

Frames would invert the layers. The parser lives in hydra-protocol, which sits above this crate. A transport that yielded Frame would need Parser below the crate Parser lives in.

So: bytes. Chunk boundaries are whatever the source gives, which is exactly what makes replaying a recording exercise the partial-line path for real.

§Why not AsyncRead + AsyncWrite

Considered and rejected. A replay source would have to impersonate a socket, and AsyncWrite::shutdown conflates “the recording ended” with “the peer hung up”, which a clean disconnect has to tell apart.

§Deadlines are the caller’s

Every wait has a deadline. That deadline is applied by the session with tokio::time::timeout, not taken as a parameter here: a timeout belongs to the policy that waits, not to the pipe. Passing one in would be a config option with one caller.
