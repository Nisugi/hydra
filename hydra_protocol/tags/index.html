KNOWN_WIRE_TAGS: every element name the wire is known to emit.

The list is knowledge of the protocol that lives nowhere else: every tag seen in recorded traffic, every tag a dispatch arm handles, and tags the game’s own client recognises though recorded traffic has not happened to carry them. It holds 126, all distinct, ASCII-sorted; the_table_holds_126_tags asserts the number.

§Entries worth a note

  • c – the echo of the player’s own typed command: <!-- CLIENT --><c>ask lu about bounty<!-- ENDCLIENT -->, always inside a <!-- CLIENT --> region. For a client that replays its own logs as fixtures, the echo is how a replay knows what the player did.
  • map, mapInfo – the automapper dialog, plain server output: <dialogData id='mapViewMain'><map id='mapViewMain' mapId='toadwort' ...> and <mapInfo id='mapViewMain' pos='14017003'/>.
  • streamBox – a text box inside a dialog: <dialogData name="bugitemReport"><streamBox id="instructions" ...>.
  • FEStart – session start, sibling of FEVersion: <FEVersion="0" character="..." /><FEStart name="..." time="1745968462" />, where name is the game’s own title. Rare: it turned up only once a sample of recorded traffic reached 3,000 files.
  • style – the room-name / room-desc preset switch, <style id="roomName" /> and <style id=""/> to close. Hundreds of thousands of occurrences, handled as markup.
  • clearDialogData – has a dispatch arm, and is listed on the handler’s authority though recorded traffic has not carried it.
  • closeContainers, room, task – recognised by the game’s own client and absent from recorded traffic. A zero in a sample means only that the sample did not contain it. task is an <objective> child carrying quest progress.
  • group – live in two distinct shapes: <group id open> client settings, and <group id type state cmd name> inside <objectives>.

Why a corpus replay cannot check this table alone. A replay counts UnknownTag { name } if !is_known(name), but is_known is consulted only at the END of dispatch, after every explicit name arm. A tag that has its own arm never reaches the check, so its table entry is invisible to the replay – and most entries have such an arm. Deleting one from the table would leave the replay green. every_tag_with_a_handler_arm_is_in_the_table is what makes the table and the dispatcher one fact instead of two.

Two categories are deliberately not listed, because neither is game protocol and both are handled structurally in crate::parser:

  • The login <settings> blob’s own element names (h, dc, cmdline, ignores, panels, …). It is a client-configuration document, and the region is consumed whole.
  • Help text that merely looks like markup – <skill#>, <#ranks>, <stat name>. An XML name cannot contain # or a space; these reach the user as text via Frame::UnknownTag.

XML comments (<!-- ... -->) are also real wire content and are handled in crate::parser, not here: a comment is not an element and has no name.

Nothing is removed lightly: a superset parser is more tolerant, never less, and removal is the risky act.

§Why the table stays sorted, and why the test is not decoration

is_known is a binary_search, so sort order is a correctness precondition, not tidiness. A mis-sorted insert makes random other tags report unknown, and they then spray into the user’s text stream. The failure is silent and affects an arbitrary subset.

The test can go RED: appending "aaa" to the end of the list fails the windows(2) scan immediately. The assertion is strict <, so it catches duplicates too – a duplicate is harmless to binary_search but means someone added a tag that was already there and should know.

The order is bytewise, so uppercase sorts before lowercase (FEVersion … PantheonStatus, then a). A case-insensitive sort would disagree with binary_search and break exactly the tags it was meant to tidy.
